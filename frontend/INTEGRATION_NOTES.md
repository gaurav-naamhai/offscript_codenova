# Frontend / backend integration notes

Compared against `origin/main` at `cda8db6` and the current frontend working tree. “Current backend support” describes implemented code; the final column contains proposals for team agreement, not existing API features.

| Frontend requirement | Current backend support | Proposed agreement |
| --- | --- | --- |
| Draft title, audience, purpose/channel, optional context and demo guidance | `Submission` and multipart create/revise accept content type, role, text or file; they have no fields for these UI values. | Agree on names, validation, optionality and persistence for metadata, including guidance identity. Include title in list summaries. Until then keep metadata local and make that limitation visible. |
| Text and file validation | Text is trimmed and limited to 50,000 Python characters. Images accept PNG, JPEG and WebP up to 5 MiB; PDFs up to 10 MiB, with signature validation. The frontend limits text to 10,000 JavaScript characters, accepts GIF as well, and has no size check. | Agree on a common text counting rule and limit, supported formats and size limits. Align client validation and handle server validation errors; do not claim GIF upload support unless the backend adds it. |
| IDs and library summaries | `POST /submissions` creates a server UUID. `GET /submissions` returns newest-first summaries containing ID, content type, status, version, creation time and flag counts, but no title or updated time. The frontend uses local UUIDs, title and updated time. | Treat server IDs as authoritative once connected; define a safe mapping/migration for local drafts. Agree on title and updated time in summaries and on ordering, search and filter behavior. |
| Assessment state | Flags have `finding_type` (`brand` or `claim`) and `state`: brand `aligned`, `potential_issue`, `unclear`; claim `supported`, `contradicted`, `insufficient_evidence`. They also include `needs_human`, `origin`, evidence, passage and a string location. | Map assessment labels separately from user decisions. Treat error-origin flags and degraded modules as incomplete checks, not passes; define reliable text ranges or image/PDF coordinates before highlighting. |
| Finding resolution | Flags have a distinct `status` (initially `open`; resolution sets `accepted` or `dismissed`). `POST /submissions/{id}/flags/{flag_id}/resolution` accepts `action: accept` or `dismiss`, optional `comment` and `role`. | Keep resolution separate from assessment and approval. Define conflict/staleness handling and whether undo is supported; the existing API has no undo route. |
| Submission workflow status | `Submission.status` is `draft`, `ai_review`, `manager_review`, `final_approval` or `approved`. The local frontend uses `Draft` and `Unreviewed`; they are not equivalent to backend review outcomes. | Define explicit UI mappings and role/state transitions. Never infer approval from a correction or absence of findings. |
| Corrections and rechecks | Accepting a text flag applies its suggested correction to the first matching passage when present. `/flags/{flag_id}/recheck` simulates a candidate without saving and returns `new_flags`, `original_flag_gone` and `has_needs_human`; it is text-only. `/revise` updates draft content. | Agree on unambiguous versioned ranges and concurrency checks for repeated passages, and how revision invalidates findings. Make clear that recheck is a preview and show unsupported image/PDF editing honestly. |
| Comments and decisions | `/comments` accepts `{role, text}` and returns a versioned comment; `/decision` accepts `{role, decision, comment?}` with `approve` or `request_changes`, subject to workflow/role checks. Detail responses include comments and decisions; `/audit` returns events. | Map these separately from local demo comments and activity. Agree on authenticated identity, authorization, error handling and version-conflict behavior before enabling consequential actions. |
| Delete | No delete route is implemented. The frontend currently deletes local records after confirmation. | Agree on deletion semantics and authorization before adding server-side support; do not present local deletion as server deletion. |
| Storage, authentication and review capability | Backend defaults to a capped in-memory repository that resets on restart; Supabase is a placeholder. Role values are checked but authentication is not implemented. Review plugins are placeholders; OCR and real external AI/search calls are not implemented. Failures produce error-origin flags and `degraded_modules`. | Keep local demo data and server data clearly distinguished. Agree on durable storage, real authentication and plugin readiness before promising persistence, security or live analysis. Surface degraded results and preserve human review requirements. |

## Adapter proposal

Introduce a typed review service interface between the UI and storage. Keep the current local implementation for demo/offline records and add a separate API implementation when the contract is agreed. The API adapter would translate multipart uploads, server IDs, status enums, versioned findings and errors into explicit UI models; it must not fabricate missing metadata, locations or successful checks. Components consume the interface rather than calling endpoints directly. Define migration and conflict handling before moving existing local records to the server, and keep file re-upload requirements visible.
